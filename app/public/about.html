The problem

Households pay for an internet speed. They cannot tell if they get it. And if they do not, they cannot prove it.

Wi-Fight is built for students, renters, and families in Huntsville, Alabama. These are people who pay the bill but have no easy way to check it.

How Proof AI works

Proof AI has two layers. The numbers come from statistics that run on your device. The words come from a large language model, or from a built-in writer when no AI key is set.

Checking Proof AI status.
Layer 1 · On this device
Real statistics
Daily median. Each day's result is the middle value of that day's tests, so one odd test cannot swing the day. median, summarize
The fair line. 80% of the download speed on the plan's label. A day under it counts as a low day. FAIR
The rule of 3 days in a row. A shortfall is flagged only when the daily median stays under the fair line for 3 days running. STREAK
One-off dip detection. Each test is compared with the tests in the 36 hours before and after it. The app computes a robust z-score from their median and their median absolute deviation. A test is ignored as a one-off only if the score is under -3.5 and the speed is under 60% of the local median. A slow stretch is not ignored, because its neighbours are slow too. flagOutliers
Wi-Fi or provider evidence score. The score starts at 50/50 and moves with each piece of evidence: the paired router check (one test next to the router, one in a far room), evening against daytime speed, the number of devices per person, and how long the problem has lasted. Each piece is shown to the user. diagnose
Plan scoring rule. The app estimates the speed a household needs from its size and uses, adds up each plan's cost over 24 months with any price jump, and picks the cheapest plan that fits. recommend
All in js/engine.js. No network call is involved.
Layer 2 · Through the local server
Language and vision by a language model
Which model. The server uses the first one available: Claude or a model hosted on Groq when a key is set, or a model running on this computer through Ollama, which needs no key and sends nothing off the device. With a local model, the short dashboard and verdict cards use the built-in writer, and the chat and the report draft use the model.
Every number is checked. The server compares each number the model writes with your data. A short answer with a number that is not in your data is discarded. A chat answer gets a visible warning.
What the model writes. The explanation on the dashboard and verdict, chat answers grounded in the user's own numbers, the report draft, and the reading of a bill photo. AI.insight AI.verdict AI.answer AI.draft AI.readBill
The key stays on the server. The browser calls /api/ai on this computer. Only the server holds an AI key and talks to the model. A key is never in the browser.
Only a trimmed set of facts is sent. The model gets a summary: first name, plan, median, days below the fair line, the dips that were ignored, the diagnosis, and bill figures if a bill was added. It does not get the email address or the raw test list. Chat also sends the question and the recent conversation. slim
The model is told to stay inside the facts. Its instructions say to use only the numbers the app gives it, and to never claim that something was sent.
Offline mode
No key, no problem. When no AI key is set, a built-in writer produces the wording from the same computed numbers, and the interface says so under every AI block. One thing needs the model: reading a real bill photo. In offline mode that step shows labelled sample values to edit.

Responsible AI
It shows its evidence. Every AI block lists the tests, days, and method behind it.

Security and privacy

Real, not decorative
Checking encryption status.
Consent before any test. The test code checks for consent first and refuses to run without it. This covers the practice test too.
Encrypted at rest. App data is saved in the browser with AES-GCM 256. The key is non-extractable, so scripts can use it but cannot read it out.
Report fingerprint. The report carries a SHA-256 fingerprint of its content, so any later change can be detected.
Approve before send. The user reads the report and approves it before it can leave the device.
AI key kept server side. The key lives in the server's settings and is never sent to the browser.
Data minimisation. Bill photos are never stored. Only the numbers read from the bill are kept.
Download and delete everything. The user can download all stored data as one file, or delete it all. Deleting also destroys the encryption key. See Privacy.
The limits, stated plainly

This is a single-device prototype with no account server. So sign-in is a demo, and there is no sync across devices. Your data lives only in this browser.

Limitations

Tests run only while the app is open. Phones do not allow reliable background tests for web apps.
The practice test is not a real measurement. It exists for networks that block M-Lab, and it is always labelled.
Provider and plan values are fictional sample values. Real label data must be entered by hand, because there is no public feed.
Slow home Wi-Fi can look like a slow provider. The paired router check is what tells them apart. Without it the app says the cause is not clear.
The diagnosis is an evidence score, not a certainty.
There is no email server. So sign-in and sending are demos.
The pilot is small and still planned. 15 student households over 4 weeks. The success measure is "12 of 15 households get a clear answer".
M-Lab publishes test results and IP addresses. The consent page says this before any real test.
